# Microsoft Intelligent Terminal (IT) + ACP — Research Report for RFC 28

> Target consumer: planning agent designing RFC 28 (OpenCode OS × IT integration). All URLs verified Jul 25 2026.

## 1. The IT repo (microsoft/intelligent-terminal)

MIT-licensed experimental fork of Windows Terminal, announced **2026-06-02** (`devblogs.microsoft.com/commandline/announcing-intelligent-terminal-version-0-1/`), 1.6k stars, 5,606 commits on `main`. Ships as MSIX (`Microsoft.IntelligentTerminal`) on Microsoft Store (`apps.microsoft.com/detail/9NMQC2SSJX24`), WinGet id `Microsoft.IntelligentTerminal`, requires Windows 10 2004 (build 19041+). First-run autodetects several ACP CLIs on PATH including **OpenCode** (per README §Get Started). NOTE: IT is an external .exe — does NOT break OpenCode OS single-binary (RFC 25 §11).

**Sub-systems (from `AGENTS.md` + `ARCHITECTURE.md`):**
- **`wta`** (Rust): orchestrator. `wta-master` (one per IT process) spawns the agent CLI once and multiplexes per-tab `wta-helper` children over a named pipe speaking ACP/JSON-RPC. Each tab pre-warms a stashed helper so autofix works on hidden panes (`tools/wta/src/app.rs:6820`).
- **`wtcli`** (C++): CLI client of the WinRT COM `IProtocolServer`. 17 sub-commands documented in `doc/wtcli-commands.md`: `list-windows`, `list-tabs`, `list-panes`, `active-pane`, `capture-pane` (scrollback; `--last-prompt` requires OSC 133), `pane-status` (pid/state/exit_code), `new-tab`, `split-pane`, `kill-pane`, `focus-pane`, `wait-for`, `listen` (long-running JSON-line stream, `--event` glob filter), `send-event` (`agent_event` envelope), `publish` (raw), `info`, `test-pipe`, `set-env`. The 4 first-class verbs any external agent uses: **read pane output**, **run command**, **wait**, **subscribe to events**. Discovery via `WT_COM_CLSID` env var + `CoCreateInstance(CLSCTX_LOCAL_SERVER)`.
- **`wt-agent-hooks`** (PowerShell plugin, bundled at `tools/wta/wt-agent-hooks/{copilot,claude,gemini-extension}/`): opt-in hooks for "Agent session tracking". Auto-upgraded per-CLI at `wta-master` startup via `agent_hooks_installer::upgrade_installed_hooks` (state cache `hooks-upgrade-state.json`). Hooks emit OSC 9001 control sequences consumed by WT and re-broadcast to `wtcli listen`.

**Slash commands advertised by IT's pane (from README + faq.md):** `/help`, `/clear`, `/new`, `/fix [hint]`, `/restart`, `/stop`, `/sessions`, `/agent [id]`, `/model [id]`. Blog 0.1.1 (Jun 17) adds bash support and "new slash commands" (gated behind the agent CLI; IT itself does not define them — they come from whichever ACP agent is loaded, see §2).

**Settings keys (`settings.json`, top-level):** `acpAgent`, `acpModel`, `acpCustomCommand`, `agentPanePosition`, `delegateAgent`, `delegateModel`, `delegateCustomCommand`, `autoFixEnabled`, and nested `aiIntegration.coordinator.{enabled,commandline,profile}` and `aiIntegration.confirmation.{readOperations,createOperations,inputOperations}` ("auto" = auto-approve). FAQ 3 admits agent-session-management only tracks Copilot/Claude/Codex/Gemini/OpenCode today.

## 2. Agent Client Protocol (ACP) — v1 stable, v2 draft

Site `agentclientprotocol.com`. Rust+TypeScript SDKs hit 1.0 on **2026-06-25** (announcement `sdk-1-0-releases`). The crate is **`agent-client-protocol` v2.0.0** on crates.io (published 2026-07-23), behind feature flags `unstable_mcp_over_acp`, `unstable_session_fork`, `unstable_protocol_v2`. The SDK is component-based ("SACP"). Companion crates `sacp-tokio`, `sacp-proxy`, `sacp-rmcp` (bridges to `rmcp` MCP), `sacp-conductor` (reference proxy-chain orchestrator).

**ACP v1 — methods an AGENT must/can implement (per `protocol/v1/overview`):**
- Baseline mandatory: `initialize`, `session/new`, `session/prompt`, `session/cancel`.
- Optional: `authenticate`, `session/load` (gated by `loadSession` cap), `session/resume` (`sessionCapabilities.resume`), `session/close` (`sessionCapabilities.close`), `session/delete` (`sessionCapabilities.delete`), `session/list` (`sessionCapabilities.list`), `session/set_mode`, `logout`, `fs/read_text_file`/`fs/write_text_file` (Client-side), `terminal/*` (Client-side), `elicitation/create` (Client-side), `mcp/connect`/`mcp/message`/`mcp/disconnect` (MCP-over-ACP).
- Notifications Agent→Client: `session/update` carrying `agent_message_chunk`, `user_message_chunk`, `thought_chunk`, `tool_call`/`tool_call_update`, `plan`/`plan_update`/`plan_removed` (RFD plan-operations, Apr 2026 draft — multi-plan via `id`, variants `items`/`markdown`/`file`, needs client-side `plan` capability), `available_commands_update` (slash command advertisement), `current_mode_update`, `session_info_update`, `session_usage_update`.

**ACP v1 — methods a CLIENT implements (what IT does):** `initialize` (with `clientCapabilities` advertising `fs.readTextFile`, `fs.writeTextFile`, `terminal`, `elicitation`, `session.configOptions.boolean`), `session/request_permission`, all `terminal/*` (create/output/wait_for_exit/kill/release), `fs/*`, `elicitation/*`. **`terminals` endpoint (`protocol/v1/terminals.md`)** is the terminal-execution surface: `terminal/create` starts a process and returns `terminalId` immediately (async semantics for background tabs), `terminal/output` polls, `terminal/wait_for_exit` blocks, `terminal/kill`, `terminal/release`; `outputByteLimit` triggers head-truncation at a char boundary. Tool calls may embed `{"type":"terminal","terminalId":...}` content for live-streaming UIs.

**v2 addenda relevant to RFC 28:** `plan-operations` RFD (multi-plan, markdown/file plan variants), `proxy-chains` RFD (conductor + `proxy/initialize`/`proxy/successor`), `session-fork` RFD (under `unstable_session_fork`), Streamable HTTP/WebSocket transport, `v2/client-filesystem-terminal-capabilities` (richer fs+terminal surface), `v2/permission-requests` (structured multi-option permission UI — see ACP spec example for exiting plan modes in `session-modes`).

**Session modes (`protocol/v1/session-modes.md`):** `ask`/`architect`/`code`/etc, switchable from Client via `session/set_mode` or Agent via `current_mode_update` notification. Architect mode typically offers a `switch_mode` tool that calls `session/request_permission` with options `{allow_always, allow_once, reject_once}` — this IS the structured "auto-approve" prompt IT surfaces.

## 3. Internal MCP / agent-event contract

IT does NOT publish an MCP server on `127.0.0.1:<port>/mcp`. The repo has no `/mcp` HTTP path. The actual in-band contract is **`IProtocolServer` over WinRT COM** (discovered via `WT_COM_CLSID`, `CoCreateInstance(CLSCTX_LOCAL_SERVER)`), surfaced through `wtcli` (tmux-style). The richer "MCP-like" channel is the **`doc/specs/llm-agent-event-integration.md`** proposal: any in-pane process emits `OSC 9001;AgentEvent;<json>\a` to stdout (Channel 1) OR calls `wtcli send-event -e <event> '<json>'` via COM (Channel 2). WT re-broadcasts both to `wtcli listen` subscribers in a single `{"type":"event","method":"agent_event","params":{"pane_id":"3","event":"agent.task.started",...}}` envelope. Standard event types proposed: `agent.started`, `agent.task.{started,completed}`, `agent.tool.{invoked,completed}`, `agent.error`, `agent.idle` (plus custom namespaces e.g. `copilot.plan.updated`). WT is a pure relay (no storage, fire-and-forget). For MCP-native agents, Proposal "Pattern D" suggests exposing `send_event` as an MCP tool from `wta` directly. The GENUINE ACP-native MCP-over-ACP path exists only at the **ACP layer** (RFD `mcp-over-acp.md`, gated `agentCapabilities.mcpCapabilities.acp`), not at the wtcli/terminal layer. **Correction to the brief: there is no `127.0.0.1:<port>/mcp` endpoint in IT.** Our swarm should instead consume via `wtcli listen --json` (Channel 2) emitting JSON lines we can parse.

## 5. Seven actionable ideas for OpenCode OS × IT (RFC 28)

**(a) ACP server in `opencode` Rust CLI.** Wire `agent-client-protocol` v2.0.0 (`features = ["unstable_mcp_over_acp","unstable_session_fork"]`) into `src-tauri/src/cli/bin/opencode.rs`. Methods we MUST implement so IT auto-detects us as a pane agent: `initialize` (advertise `agentCapabilities.{loadSession:true, sessionCapabilities:{resume:{}, close:{}, delete:{}, list:{}}, mcpCapabilities:{http:true, acp:true}, promptCapabilities:{embeddedContext:true}, auth.logout:{}}`), `session/new`, `session/prompt`, `session/cancel` (baseline required), plus optional `session/load` (replay Journal M1–M12 to the pane via `session/update`), `session/resume`, `session/close`, `session/delete`, `session/list`, `session/set_mode` (maps to RFC 19 Execution Supervisor states: PLAN→architect, EXEC→code, REVIEW→ask), and `logout`. Advertise slash commands via `available_commands_update`: `/opencode mission new <prompt>`, `/opencode fork`, `/opencode resume`, `/opencode exec step`. Use the `sacp-tokio` runtime helper to drive the JSON-RPC stdio loop inside our existing `tokio` runtime. Reuse `crates.io/crates/agent-client-protocol` — the announcement confirms IT ships against the same SDK.

**(b) Swarm engines consume IT terminal context via `wtcli listen --json`.** Spawn one Rust task per IT window subscribed to `wtcli listen --event "agent.*"` and `--event "pane.process.*"` (Phase 2 events from `llm-agent-event-integration.md`). Each JSON line tagged `agent.tool.completed` with non-zero `exit_code` → Planning engine signal; `agent.task.completed` → Validator engine signal (M2 Validation per RFC 14). `agent.tool.invoked` records tool+args in Journal M6. This is the bridge from "terminal UX events" into the swarm Planner→Coder→Validator→Repair→Learning loop WITHOUT requiring IT to host our agents. Pair with `wtcli capture-pane -t <id> --last-prompt` for full scrollback on error events.

**(c) HUD vs IT pane.** HUD Mission Control (RFC 24) stays the canonical visual surface for mission plan diffs, annotations, multi-mission forks, and the doom-loop state machine (RFC 19). IT becomes the *lightweight daily entrance*: user types `/opencode mission new "fix lint"` in the pane; our ACP agent creates the mission, streams the planner `plan` notification back to the pane (visible checklist), but full IQ visual diffs/fork-tree still live in HUD. Recommendation: do NOT move Mission Control into IT (pane is a chat, not a HUD); instead expose HUD URLs via `_meta.hud_url` in `agent.task.completed` events so IT can deep-link into the desktop app. Future UX "pane-as-HUD" is limited by ACP's lack of structured diff rendering beyond markdown — defer until ACP v2 `v2/diff-file-states` stabilizes.

**(d) Hooks → Journal M14 `agent_session_events`.** Persist every `agent_event` JSON line into a new SQLite table `M14_agent_session_events` (id, ts, pane_id, event_type, agent, task_id, payload_json) for doom-loop audit and replay. The `wt-agent-hooks` PowerShell bundle (or our own fork) wraps `opencode` so SessionStart/Stop/ToolCall	events flow as OSC 9001 sequences from inside any shell pane. This gives Execution Supervisor (RFC 19) real-time cross-agent observability without polling. Reuse `journal/schema` migration pattern from `OpenCode OS/03 - Memory & Journal.md`.

**(e) `?<prompt>` + `--auto-approve` vs `opencode mission --auto`.** IT's Command Palette `?<prompt>` routes to the **delegate-agent** (Alt+Shift+B / Alt+Shift+/) which by spec uses the agent CLI's **default model** with no per-tab mode preselected (faq Q7). Map our `opencode mission --auto` to the delegate path: pre-set session mode `code` from `session/new` response, advertise `confirmation.readOperations=auto` equivalent on the ACP side via `session/set_mode` plus `session/request_permission` options `{allow_always}` (exactly the architect-mode exit pattern from `session-modes.md`). For security (RFC 19 §permission), never auto-approve `createOperations`/`inputOperations` in the delegate path — only the explicit `--auto` mission flag flips them.

**(f) `/fix [hint]` and `/restart`.** ACP advertises these as `AvailableCommand`s with optional `{hint: string}` input ("unstructured text input" per `slash-commands.md`). Implement `/opencode fix [hint]` as a custom command we `available_commands_update`-advertise: it captures `wtcli active-pane` + `capture-pane --last-prompt`, packages the last non-zero exit as a `session/prompt` content block of type `Resource` (link to the captured scrollback), and routes it to the Repair engine (RFC 15). `/opencode restart` calls `session/close` then `session/new` with the same `cwd` — wires cleanly to our existing `opencode resume` (load) and `opencode fork` (new.branch via `unstable_session_fork`). Both are zero-UI: user types them in the IT pane, our binary handles the ACP method.

**(g) `opencode exec step` → IT delegate tab (Alt+Shift+B).** Alt+Shift+B opens an interactive delegate-agent tab with no startup prompt. Wire our `opencode exec step <mission_id> <step_id>` as the delegate CLI command (no args = step picker). When invoked, it connects via ACP, calls `session/new` with `cwd=mission_cwd`, immediately `session/prompt`s with a synthesized "execute step X" user message, and streams the swarm's progress as `plan_update`+`tool_call_update` notifications so the pane shows a real background agent. Because the delegate uses the agent CLI's default model, configure `delegateAgent=opencode` in IT Settings.json user-pref dump (or our installer writes it). One subtlety: agent-session-management only tracks the SAME agent for pane and delegate (faq Q8) — recommend pinning both to `opencode` so delegate tabs also appear in our HUD's session list.
